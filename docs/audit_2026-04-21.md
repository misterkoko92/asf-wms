# Audit global ASF WMS — 21 avril 2026

Audit transversal du dépôt (architecture, sécurité, scalabilité, évolutivité, utilisabilité, qualité, ops, conformité). Complète l'audit [2026-02-19](audit_2026-02-19.md) en élargissant le périmètre à la scalabilité, l'ops, la conformité RGPD et la préparation aux features IA.

> **Contexte auteur** : projet maintenu principalement par un non-développeur assisté par IA (Codex, Claude Code). Les recommandations tiennent compte de ce contexte — priorité aux gains de sécurité rapides et aux fondations qui préviennent la dette, plutôt qu'aux refactorisations lourdes.

> **Mise à jour 2026-04-22** : la Phase A sécurité critique a été implémentée dans `asf_wms/settings.py` et n'est plus un risque ouvert. Les priorités ci-dessous distinguent désormais les points corrigés, les risques encore ouverts, et les chantiers à garder en roadmap.

## 1) Méthode et périmètre

Audit exécuté sur :

- Arbo globale : `wms/`, `contacts/`, `api/`, `asf_wms/`, `templates/`, `deploy/`, `docs/`, `tools/`
- Configuration : `settings.py`, `pyproject.toml`, `mypy.ini`, `pyrightconfig.json`, `.pre-commit-config.yaml`, `.github/workflows/`, `Makefile`
- Volumétrie code : ~220 fichiers Python dans `wms/`, 24 dans `api/`, 19 dans `contacts/`, 248 templates, 275 fichiers de test
- Dépendances : `requirements.txt`, `requirements-dev.txt`, `uv.lock`

Aspects **non explorés dans cet audit** (à auditer séparément si besoin) :
- Exécution dynamique (benchmarks, profiling, charge)
- Base de données réelle en production (volumétrie, plans d'exécution)
- Tests end-to-end navigateur (Playwright)
- Audit accessibilité WCAG avec outils (axe, Lighthouse)
- Pénétration test externe
- Revue des données réelles (fuite potentielle dans les fixtures)

## 2) Résumé exécutif

### Forces majeures

- Architecture domaine bien séparée (`wms/models_domain/`, `wms/application/`)
- CI solide : ruff, mypy (partiel), pyright (shadow), bandit, detect-secrets, couverture 93 % imposée
- 275 fichiers de test mirroring la production
- PWA fonctionnelle avec service worker et cache offline
- Infrastructure i18n présente côté templates ; le sélecteur visible reste volontairement masqué tant que le scope traduction est pausé
- 0 TODO/FIXME/HACK dans le code — dette trackée dans `docs/`
- Pattern event-driven via `IntegrationEvent` — extensible
- Référence de maintenance centralisée dans `docs/repo-reference/`

### Risques principaux (par ordre décroissant)

1. **Conformité RGPD / juridique** non formalisée — données personnelles et documents sensibles sans politique explicite dans le produit
2. **Monitoring/alerting absent** — incidents production visibles seulement par remontée utilisateur
3. **PRA/backups insuffisamment formalisés** — procédure de base présente, mais pas encore de test de restauration ni de couverture MEDIA/secrets
4. **Sécurité secondaire API/tracking** — comparaison de clé API, throttling DRF, politique d'expiration/rate limit des accès de suivi
5. **Licence / CGU / politique de confidentialité absentes** — ambiguïté juridique pour contributeurs, utilisateurs portail et associations tierces
6. **Performance à surveiller** — pas un risque critique au volume actuel, mais les requêtes stock/dashboard doivent être profilées avant croissance

## 3) Findings détaillés

### A. Sécurité

#### Critique — corrigé par la Phase A (✅)

1. **Flags cookies sécurisés** [`asf_wms/settings.py`](../asf_wms/settings.py)
   - Présents : `SESSION_COOKIE_HTTPONLY`, `SESSION_COOKIE_SAMESITE="Strict"`, `CSRF_COOKIE_HTTPONLY`, `CSRF_COOKIE_SAMESITE="Strict"`
   - Statut : fermé

2. **`DEBUG=False` par défaut** [`asf_wms/settings.py`](../asf_wms/settings.py)
   - `DJANGO_DEBUG` est maintenant opt-in
   - Statut : fermé

3. **`SECRET_KEY` obligatoire** [`asf_wms/settings.py`](../asf_wms/settings.py)
   - Plus de fallback hardcodée hors tests
   - Statut : fermé

4. **`DOCUMENT_SCAN_BACKEND=noop` interdit hors tests**
   - Le démarrage échoue si `noop` est configuré hors test Django
   - Statut : fermé

5. **Endpoint legacy tracking opt-in**
   - `ENABLE_SHIPMENT_TRACK_LEGACY` vaut maintenant `False` par défaut
   - Statut : fermé

#### Important (🟠)

1. **Comparaison API key non timing-safe** [`api/v1/permissions.py:10`](../api/v1/permissions.py) → utiliser `hmac.compare_digest`
2. **Pas de throttling DRF** sur les endpoints publics — ajouter `DEFAULT_THROTTLE_CLASSES`
3. **Accès de suivi expédition sans politique complète de rate limit / expiration** [`wms/views_scan_shipments.py`](../wms/views_scan_shipments.py)
   - Les scans QR passent maintenant par un token UUID et un gateway d'identité, mais il manque une politique explicite d'expiration, rotation ou limitation des tentatives selon le contexte métier.
4. **Mot de passe minimum à 8 caractères** — Django défaut, à passer à 12
5. **Pas de 2FA admin** — sensible pour un compte avec accès à toutes les données

#### Déjà bien (✅)

- `defusedxml` pour parsing XML
- `detect-secrets` + baseline signée
- `bandit` dans CI
- `SECURE_SSL_REDIRECT`, `SECURE_HSTS_*` correctement configurés quand `DEBUG=False`
- Tests dédiés aux defaults sécurité (`wms/tests/core/tests_security_settings.py`)

### B. Maintenabilité

#### À améliorer (🟠)

1. **Fichiers trop volumineux**
   - [`api/v1/ui_views.py`](../api/v1/ui_views.py) : 2 824 lignes ⚠️
   - [`wms/views_scan_shipments.py`](../wms/views_scan_shipments.py) : ~2 000 lignes
   - [`wms/views_portal_account.py`](../wms/views_portal_account.py) : 1 776 lignes
   - [`wms/admin.py`](../wms/admin.py) : 1 650 lignes
   - Recommandation : découper par cas d'usage (pattern déjà appliqué ailleurs)

2. **Typage partiel** — mypy scopé à `wms/application/`, `wms/events/`, `wms/jobs/`, `wms/parties/`, `wms/artifacts/`. Pyright en mode `standard` (non `strict`). Étendre progressivement.

3. **Ruff minimaliste** — seulement `E9, F63, F7, F82, I, UP`. Ajouter progressivement `B` (bugbear), `SIM`, `RUF`.

4. **Documentation d'architecture à maintenir, pas à créer de zéro**
   - `docs/repo-reference/` est désormais la référence canonique.
   - Recommandation : garder cette référence alignée à chaque changement critique, et n'ajouter un `docs/architecture/overview.md` que si un schéma plus visuel devient utile.

#### Déjà bien (✅)

- Séparation domaine stricte
- Pattern `handlers/helpers/application layer`
- 0 marqueur de dette dans le code
- CI complète

### C. Scalabilité et performance

#### Important, mais non critique au volume actuel (🟠)

1. **Stratégie d'index DB à vérifier par plans d'exécution** [`wms/models_domain/inventory.py`](../wms/models_domain/inventory.py), [`wms/models_domain/portal.py`](../wms/models_domain/portal.py)
   - Correction importante : l'absence de `db_index=True` explicite sur les `ForeignKey` ne signifie pas forcément absence d'index, Django indexant les FK par défaut.
   - Risque réel : absence possible d'index composites adaptés aux filtres/sorts des cockpits stock, réception, suivi et dashboard.
   - Recommandation : profiler les requêtes lentes (`EXPLAIN`, Django Debug Toolbar en dev) avant d'ajouter des migrations d'index.

2. **Cache applicatif non exploité pour les cockpits**
   - Le cache Django existe implicitement si `CACHES` n'est pas configuré, et le code l'utilise déjà pour certains throttles.
   - Risque réel : aucun cache ciblé n'est appliqué aux vues dashboard/pilotage potentiellement coûteuses.
   - Priorité : seulement après profiling ; éviter un cache prématuré qui masquerait des règles métier fraîches.

#### À surveiller selon évolution du volume

3. **Files d'attente en polling synchrone** (email, scan doc, print) — OK pour volume associatif actuel, bloquant au-delà de ~500 expéditions/jour
4. **Sessions en DB** par défaut — lecture DB à chaque requête
5. **MEDIA sur filesystem local** — non scalable au-delà d'une instance

#### Déjà bien (✅)

- `IntegrationEvent` correctement indexé
- 449 occurrences de `select_related`/`prefetch_related`
- Modèle domaine déjà extrait en couche `application/`

### D. Évolutivité

#### Forces (✅)

- Domaine extensible : nouveau type d'expédition = nouvel enum + handler
- `IntegrationEvent` = pattern event-driven pour nouvelles intégrations
- API versionnée (`/api/v1/`)
- Couche `application/` = séparation business/Django

#### À préparer (🟠)

1. **Pas de préparation IA** — aucune couche `ai/` dédiée. Quand features IA arriveront : risque de couplage direct avec Anthropic/OpenAI depuis les views.
2. **Frontend couplé serveur** — ajouter du temps réel (notif scan → dashboard) demandera ASGI/WebSockets
3. **Pas d'OpenAPI/Swagger** — ajouter `drf-spectacular` pour doc API auto-générée
4. **Pas de feature flags gérés** — les flags actuels (`ENABLE_*`) sont des variables d'env simples, sans observabilité

### E. Utilisabilité (UX/UI) et accessibilité

#### Forces (✅)

- PWA fonctionnelle avec service worker ([`wms/static/scan/`](../wms/static/scan/))
- Design system robuste (90+ custom properties dans [`templates/includes/design_vars_style.html`](../templates/includes/design_vars_style.html))
- Responsive Bootstrap 5.3.3
- i18n techniquement présente, avec sélecteur visible masqué par politique de pause traduction
- 53 attributs ARIA dans les templates scan

#### À améliorer (🟠)

1. **Pas de pages 404/500 custom** — UX d'erreur par défaut Django
2. **Pas de feedback audio/haptique sur scan** — gain ergonomique majeur pour le personnel
3. **Traduction EN volontairement pausée**
   - Le sélecteur langue est masqué dans les partials partagés.
   - Ne pas rouvrir ce chantier sans demande explicite.
4. **Touch targets non audités** (minimum 44×44 px mobile)
5. **Pas d'audit WCAG** outillé (axe-core, Lighthouse)
6. **Admin Django non customisé** — limitant si des bénévoles l'utilisent
7. **Pas de file d'attente offline PWA** — un scan fait hors ligne semble perdu (à vérifier)

### F. Tests et qualité (ajouté)

#### Forces (✅)

- 93 % de couverture imposée en CI
- 275 fichiers de test structurés par domaine
- Pre-commit hooks complets

#### À améliorer (🟠)

1. **Fichiers de tests très volumineux** (jusqu'à plusieurs milliers de lignes) — découper progressivement quand une zone est modifiée
2. **Pas de tests E2E navigateur legacy** (Playwright) — les flux scan/portail legacy ne sont pas couverts bout-en-bout par navigateur

Note : le seuil de couverture est déjà appliqué par `make coverage` via `COVERAGE_FAIL_UNDER=93` et par la CI ; ne pas dupliquer ce seuil dans `.coveragerc` sans raison.

### G. Déploiement et opérations (ajouté)

#### Critique (🔴)

1. **Monitoring/alerting absent** — pas de Sentry, pas de logging structuré. Incidents prod invisibles.
2. **Backups/PRA insuffisamment documentés** — `docs/operations.md` contient des commandes DB de base, mais pas encore une procédure complète DB + MEDIA + secrets + test de restauration
3. **Pas d'environnement staging documenté** — mise en prod directe depuis dev

#### Important (🟠)

4. **Dependabot activé** — `.github/dependabot.yml` existe pour `pip` et GitHub Actions ; vérifier seulement que les PR sont bien traitées régulièrement
5. **`pip-audit` informationnel** en CI — à passer bloquant sur HIGH/CRITICAL quand les faux positifs et contraintes PythonAnywhere sont maîtrisés
6. **Pas de doc "quel hébergeur pour quel volume"** — PythonAnywhere Free tier limitant, mais suffisant pour le volume actuel

### H. Conformité et juridique (nouvel aspect, non couvert avant) 🆕

#### Critique (🔴)

1. **Pas de `LICENSE` à la racine** — ambiguïté juridique sur l'usage/distribution du code. Critique si des contributeurs externes ou forks existent, ou si une asso tierce veut reprendre le projet.

2. **Politique RGPD absente** — le projet manipule :
   - Données personnelles de destinataires (nom, adresse, téléphone, email)
   - Données de bénévoles (comptes, rôles)
   - Données de contacts (expéditeurs, donateurs)
   - Documents uploadés (potentiellement données sensibles)

   **Obligations non documentées** :
   - Registre des traitements (art. 30 RGPD)
   - Mentions légales / politique de confidentialité (portail public)
   - Droit d'accès / rectification / effacement / portabilité
   - Durées de conservation
   - Sous-traitants (PythonAnywhere, Brevo email, etc.)

3. **Pas de CGU sur le portail** — les associations qui créent un compte n'acceptent rien formellement

#### Important (🟠)

4. **Pas d'export RGPD-compliant** — une personne qui demande ses données doit pouvoir les obtenir. Aucune commande dédiée.
5. **Pas de purge automatique** — données de destinataires non utilisés depuis X années non purgées
6. **Logs potentiellement sensibles** — aucun scrubber PII documenté dans la config logging

### I. Gouvernance et contribution (nouvel aspect) 🆕

1. **Onboarding contributeur** — [`README.md`](../README.md) et [`AGENTS.md`](../AGENTS.md) sont denses. Un `CONTRIBUTING.md` court (5-10 lignes) aiderait.
2. **Pas de template PR/Issue** — `.github/PULL_REQUEST_TEMPLATE.md` absent
3. **CODEOWNERS absent** — OK si solo, utile si l'asso recrute des contributeurs
4. **Pas de changelog utilisateur** (`CHANGELOG.md`) — utile pour les bénévoles qui voient des évolutions

### J. Données et résilience (nouvel aspect) 🆕

1. **Migrations de données (`RunPython`) avec rollback souvent `noop`**
   - Le dépôt contient plus que 5 `RunPython`; certains ont un reverse réel, d'autres un `noop` volontaire.
   - Ne pas réécrire l'historique de migrations sans nécessité forte.
   - Recommandation : documenter la règle future ("reverse réel ou justification du noop") et auditer les migrations critiques avant chaque rollback production.
2. **Imports CSV sans validation stricte documentée** — risque de corruption silencieuse si fichier mal formé
3. **Pas de vérification d'intégrité périodique** — un cron `check_referential_integrity` n'existe pas

### K. Préparation IA (nouvel aspect, pour anticipation) 🆕

Tu mentionnes des features IA à terme. Recommandations proactives :

1. **Créer `wms/ai/` isolé** avec clients par fournisseur — jamais d'appel direct depuis les views
2. **Utiliser prompt caching Anthropic** (-90 % coût sur prompts longs récurrents)
3. **Tracer appels IA** via `IntegrationEvent` (coûts, latence, erreurs)
4. **Rate limit par utilisateur / budget quotidien**
5. **Pseudonymisation avant envoi aux API externes** — RGPD
6. **Politique explicite dans la CGU** si l'IA traite des données utilisateur

## 5) Points à clarifier avec toi (décisions utilisateur)

Certaines recommandations nécessitent ton arbitrage avant action :

1. **Licence** — quelle licence appliquer au code ? (MIT simple, AGPL si tu veux protéger le caractère libre, licence interne asso…)
2. **Périmètre RGPD** — as-tu désigné un DPO ou référent RGPD ? Existe-t-il déjà des documents asso que je pourrais intégrer ?
3. **CGU / confidentialité** — qui valide juridiquement les textes visibles par les associations et destinataires ?
4. **Hébergement cible** — rester sur PythonAnywhere Free ou prévoir un palier payant/VPS ? Ça change les recommandations ops et sauvegardes.
5. **Multi-contributeurs** — le projet restera-t-il solo ou des bénévoles tech pourraient-ils contribuer ?
6. **Volume cible** — combien d'expéditions/mois attendues dans 1 an ? 2 ans ?
7. **Features IA** — quelles fonctionnalités envisagées (génération de communications, classement produits, prédiction, assistant bénévole…) ?

## 6) Prochaine étape recommandée

**Commencer par la Phase B (conformité et juridique)** — la Phase A est terminée, et les risques restants les plus importants sont RGPD, politique de confidentialité, CGU et licence.

Ensuite, enchaîner sur la Phase C ops : Sentry, procédure backup complète et test de restauration. Les phases performance, maintenabilité et IA restent utiles, mais ne doivent pas passer devant conformité et exploitation.
