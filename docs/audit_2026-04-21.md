# Audit global ASF WMS — 21 avril 2026

Audit transversal du dépôt (architecture, sécurité, scalabilité, évolutivité, utilisabilité, qualité, ops, conformité). Complète l'audit [2026-02-19](audit_2026-02-19.md) en élargissant le périmètre à la scalabilité, l'ops, la conformité RGPD et la préparation aux features IA.

> **Contexte auteur** : projet maintenu principalement par un non-développeur assisté par IA (Codex, Claude Code). Les recommandations tiennent compte de ce contexte — priorité aux gains de sécurité rapides et aux fondations qui préviennent la dette, plutôt qu'aux refactorisations lourdes.

## 1) Méthode et périmètre

Audit exécuté sur :

- Arbo globale : `wms/`, `contacts/`, `api/`, `asf_wms/`, `templates/`, `deploy/`, `docs/`, `tools/`
- Configuration : `settings.py`, `pyproject.toml`, `mypy.ini`, `pyrightconfig.json`, `.pre-commit-config.yaml`, `.github/workflows/`, `Makefile`
- Volumétrie code : ~220 fichiers Python dans `wms/`, 24 dans `api/`, 19 dans `contacts/`, 248 templates, 275 fichiers de test
- Dépendances : `requirements.txt`, `requirements-dev.txt`, `uv.lock`

Aspects **non explorés dans cet audit** (à auditer séparément si besoin) :
- Exécution dynamique (benchmarks, profiling, charge)
- Base de données réelle en production (volumétrie, plans d'exécution)
- Tests end-to-end navigateur (Playwright)
- Audit accessibilité WCAG avec outils (axe, Lighthouse)
- Pénétration test externe
- Revue des données réelles (fuite potentielle dans les fixtures)

## 2) Résumé exécutif

### Forces majeures

- Architecture domaine bien séparée (`wms/models_domain/`, `wms/application/`)
- CI solide : ruff, mypy (partiel), pyright (shadow), bandit, detect-secrets, couverture 93 % imposée
- 275 fichiers de test mirroring la production
- PWA fonctionnelle avec service worker et cache offline
- i18n rigoureuse (1 169+ balises `trans`) côté templates
- 0 TODO/FIXME/HACK dans le code — dette trackée dans `docs/`
- Pattern event-driven via `IntegrationEvent` — extensible

### Risques principaux (par ordre décroissant)

1. **Sécurité cookies** (HTTPONLY/SAMESITE manquants) — risque XSS amplifié
2. **Conformité RGPD** non documentée — données personnelles (bénévoles, destinataires, donateurs) sans politique explicite
3. **Indexes DB absents** sur modèles de stock — dégradation garantie à volume
4. **Pas de monitoring/alerting** en production — incidents invisibles
5. **Backups/PRA non documentés** — risque de perte de données
6. **Pas de LICENSE** — ambiguïté juridique sur le code

## 3) Findings détaillés

### A. Sécurité

#### Critique (🔴)

1. **Flags cookies manquants** [`asf_wms/settings.py`](../asf_wms/settings.py)
   - Absents : `SESSION_COOKIE_HTTPONLY`, `SESSION_COOKIE_SAMESITE`, `CSRF_COOKIE_HTTPONLY`, `CSRF_COOKIE_SAMESITE`
   - Impact : XSS peut exfiltrer les cookies ; CSRF cross-site moins contraint
   - Effort : ~5 minutes

2. **`DEBUG=True` par défaut** [`asf_wms/settings.py:47`](../asf_wms/settings.py)
   - Un oubli de variable d'environnement expose stack traces complètes en prod
   - Effort : 2 minutes (inverser le défaut)

3. **`SECRET_KEY` fallback hardcodée** [`asf_wms/settings.py:45`](../asf_wms/settings.py)
   - `"dev-secret-key-change-this"` — protection seulement si `DEBUG=False`
   - Effort : 5 minutes (faire planter si absente même en dev)

4. **`DOCUMENT_SCAN_BACKEND=noop` silencieux**
   - Mode test désactive tout scan antivirus sans blocage
   - Effort : 15 minutes (refuser `noop` hors environnement de test)

#### Important (🟠)

5. **Comparaison API key non timing-safe** [`api/v1/permissions.py:10`](../api/v1/permissions.py) → utiliser `hmac.compare_digest`
6. **Pas de throttling DRF** sur les endpoints publics — ajouter `DEFAULT_THROTTLE_CLASSES`
7. **Token de suivi expédition sans rate limit ni expiration** [`wms/views_scan_shipments.py:1816`](../wms/views_scan_shipments.py)
8. **Mot de passe minimum à 8 caractères** — Django défaut, à passer à 12
9. **Pas de 2FA admin** — sensible pour un compte avec accès à toutes les données
10. **Endpoint legacy tracking activé par défaut** (`ENABLE_SHIPMENT_TRACK_LEGACY=True`) — inverser le défaut

#### Déjà bien (✅)

- `defusedxml` pour parsing XML
- `detect-secrets` + baseline signée
- `bandit` dans CI
- `SECURE_SSL_REDIRECT`, `SECURE_HSTS_*` correctement configurés quand `DEBUG=False`

### B. Maintenabilité

#### À améliorer (🟠)

1. **Fichiers trop volumineux**
   - [`api/v1/ui_views.py`](../api/v1/ui_views.py) : 2 824 lignes ⚠️
   - [`wms/views_scan_shipments.py`](../wms/views_scan_shipments.py) : 1 977 lignes
   - [`wms/views_portal_account.py`](../wms/views_portal_account.py) : 1 776 lignes
   - [`wms/admin.py`](../wms/admin.py) : 1 650 lignes
   - Recommandation : découper par cas d'usage (pattern déjà appliqué ailleurs)

2. **Typage partiel** — mypy scopé à `wms/application/`, `wms/events/`, `wms/jobs/`, `wms/parties/`, `wms/artifacts/`. Pyright en mode `standard` (non `strict`). Étendre progressivement.

3. **Ruff minimaliste** — seulement `E9, F63, F7, F82, I, UP`. Ajouter progressivement `B` (bugbear), `SIM`, `RUF`.

4. **Pas d'architecture doc centralisée** — 20+ plans dans `docs/plans/`, mais aucun schéma global. Bénéfice direct : Claude/Codex produisent des propositions plus cohérentes.

#### Déjà bien (✅)

- Séparation domaine stricte
- Pattern `handlers/helpers/application layer`
- 0 marqueur de dette dans le code
- CI complète

### C. Scalabilité et performance

#### Critique (🔴)

1. **Indexes DB manquants** [`wms/models_domain/inventory.py`](../wms/models_domain/inventory.py), [`wms/models_domain/portal.py`](../wms/models_domain/portal.py)
   - Un seul `db_index=True` sur l'ensemble du projet (hors `IntegrationEvent`)
   - Manquants critiques : `ProductLot.product`, `ProductLot.location`, `Receipt.warehouse`, `Receipt.source_contact`
   - Dégradation garantie dès ~10k lots

2. **Aucune couche de cache** — pas de `CACHES` dans settings.py, pas de `@cache_page` ni `@cached_property` sur les vues dashboard

#### Important (🟠)

3. **Files d'attente en polling synchrone** (email, scan doc, print) — OK pour volume associatif actuel, bloquant au-delà de ~500 expéditions/jour
4. **Sessions en DB** par défaut — lecture DB à chaque requête
5. **MEDIA sur filesystem local** — non scalable au-delà d'une instance

#### Déjà bien (✅)

- `IntegrationEvent` correctement indexé
- 449 occurrences de `select_related`/`prefetch_related`
- Modèle domaine déjà extrait en couche `application/`

### D. Évolutivité

#### Forces (✅)

- Domaine extensible : nouveau type d'expédition = nouvel enum + handler
- `IntegrationEvent` = pattern event-driven pour nouvelles intégrations
- API versionnée (`/api/v1/`)
- Couche `application/` = séparation business/Django

#### À préparer (🟠)

1. **Pas de préparation IA** — aucune couche `ai/` dédiée. Quand features IA arriveront : risque de couplage direct avec Anthropic/OpenAI depuis les views.
2. **Frontend couplé serveur** — ajouter du temps réel (notif scan → dashboard) demandera ASGI/WebSockets
3. **Pas d'OpenAPI/Swagger** — ajouter `drf-spectacular` pour doc API auto-générée
4. **Pas de feature flags gérés** — les flags actuels (`ENABLE_*`) sont des variables d'env simples, sans observabilité

### E. Utilisabilité (UX/UI) et accessibilité

#### Forces (✅)

- PWA fonctionnelle avec service worker ([`wms/static/scan/`](../wms/static/scan/))
- Design system robuste (90+ custom properties dans [`templates/includes/design_vars_style.html`](../templates/includes/design_vars_style.html))
- Responsive Bootstrap 5.3.3
- i18n très bien appliquée
- 53 attributs ARIA dans les templates scan

#### À améliorer (🟠)

1. **Pas de pages 404/500 custom** — UX d'erreur par défaut Django
2. **Pas de feedback audio/haptique sur scan** — gain ergonomique majeur pour le personnel
3. **EN incomplet** — pas de `.mo` compilés, traductions stub. Décision à prendre : finaliser ou masquer la langue
4. **Touch targets non audités** (minimum 44×44 px mobile)
5. **Pas d'audit WCAG** outillé (axe-core, Lighthouse)
6. **Admin Django non customisé** — limitant si des bénévoles l'utilisent
7. **Pas de file d'attente offline PWA** — un scan fait hors ligne semble perdu (à vérifier)

### F. Tests et qualité (ajouté)

#### Forces (✅)

- 93 % de couverture imposée en CI
- 275 fichiers de test structurés par domaine
- Pre-commit hooks complets

#### À améliorer (🟠)

1. **`fail_under` absent de `.coveragerc`** — couverture imposée seulement en CI, pas localement
2. **Fichiers de tests très volumineux** (jusqu'à 4 152 lignes) — découper pour vélocité
3. **Pas de tests E2E navigateur** (Playwright) — les flux scan/portail ne sont pas couverts bout-en-bout

### G. Déploiement et opérations (ajouté)

#### Critique (🔴)

1. **Monitoring/alerting absent** — pas de Sentry, pas de logging structuré. Incidents prod invisibles.
2. **Backups non documentés** — pas de procédure claire DB + MEDIA + secrets
3. **Pas d'environnement staging documenté** — mise en prod directe depuis dev

#### Important (🟠)

4. **Dependabot non activé** — vulnérabilités des dépendances non détectées automatiquement
5. **`pip-audit` informationnel** en CI — à passer bloquant sur HIGH/CRITICAL
6. **Pas de doc "quel hébergeur pour quel volume"** — PythonAnywhere Free tier limitant

### H. Conformité et juridique (nouvel aspect, non couvert avant) 🆕

#### Critique (🔴)

1. **Pas de `LICENSE` à la racine** — ambiguïté juridique sur l'usage/distribution du code. Critique si des contributeurs externes ou forks existent, ou si une asso tierce veut reprendre le projet.

2. **Politique RGPD absente** — le projet manipule :
   - Données personnelles de destinataires (nom, adresse, téléphone, email)
   - Données de bénévoles (comptes, rôles)
   - Données de contacts (expéditeurs, donateurs)
   - Documents uploadés (potentiellement données sensibles)

   **Obligations non documentées** :
   - Registre des traitements (art. 30 RGPD)
   - Mentions légales / politique de confidentialité (portail public)
   - Droit d'accès / rectification / effacement / portabilité
   - Durées de conservation
   - Sous-traitants (PythonAnywhere, Brevo email, etc.)

3. **Pas de CGU sur le portail** — les associations qui créent un compte n'acceptent rien formellement

#### Important (🟠)

4. **Pas d'export RGPD-compliant** — une personne qui demande ses données doit pouvoir les obtenir. Aucune commande dédiée.
5. **Pas de purge automatique** — données de destinataires non utilisés depuis X années non purgées
6. **Logs potentiellement sensibles** — aucun scrubber PII documenté dans la config logging

### I. Gouvernance et contribution (nouvel aspect) 🆕

1. **Onboarding contributeur** — [`README.md`](../README.md) et [`AGENTS.md`](../AGENTS.md) sont denses. Un `CONTRIBUTING.md` court (5-10 lignes) aiderait.
2. **Pas de template PR/Issue** — `.github/PULL_REQUEST_TEMPLATE.md` absent
3. **CODEOWNERS absent** — OK si solo, utile si l'asso recrute des contributeurs
4. **Pas de changelog utilisateur** (`CHANGELOG.md`) — utile pour les bénévoles qui voient des évolutions

### J. Données et résilience (nouvel aspect) 🆕

1. **Migrations de données (`RunPython`) sans rollback** — 5 migrations de données détectées (0016, 0033, 0037, 0041, 0043). Pas de `reverse_code` documenté → risque en cas de rollback urgent.
2. **Imports CSV sans validation stricte documentée** — risque de corruption silencieuse si fichier mal formé
3. **Pas de vérification d'intégrité périodique** — un cron `check_referential_integrity` n'existe pas

### K. Préparation IA (nouvel aspect, pour anticipation) 🆕

Tu mentionnes des features IA à terme. Recommandations proactives :

1. **Créer `wms/ai/` isolé** avec clients par fournisseur — jamais d'appel direct depuis les views
2. **Utiliser prompt caching Anthropic** (-90 % coût sur prompts longs récurrents)
3. **Tracer appels IA** via `IntegrationEvent` (coûts, latence, erreurs)
4. **Rate limit par utilisateur / budget quotidien**
5. **Pseudonymisation avant envoi aux API externes** — RGPD
6. **Politique explicite dans la CGU** si l'IA traite des données utilisateur
